### 1.2 GBDK 2bpp Format in `dandy-gb/src/tiles.c`
- **Location**: `dandy-gb/src/tiles.c:5-102`
- **Array**: `const unsigned char dandy_tiles[]`
- **Size**: 512 bytes (32 tiles * 16 bytes/tile).
- **Format**: Planar 2bpp. Each row of 8 pixels is represented by 2 bytes:
  - First byte: Least significant bit (bit 0) of the color index for each of the 8 pixels.
  - Second byte: Most significant bit (bit 1) of the color index for each of the 8 pixels.
  - Bits are MSB-first: Pixel 0 is bit 7, Pixel 7 is bit 0.
- **Header (`dandy-gb/src/tiles.h`)**:
  Declares `extern const unsigned char dandy_tiles[32 * 16];`
- **Tile definitions**: The tiles are programmatically generated by `dandy-gb/tools/compile_bmp_sprites.py` using character art arrays (the `GLYPHS` dictionary) and written to `tiles.c` and `tiles.h`.

### 1.3 Build Process in `dandy-gb/Makefile`
- **Target**: `bin/dandy.gb` compiled via GBDK compiler utility `lcc`
- **Makefile rules**:
  - `levels`: Runs `python3 tools/convert_levels.py`
  - `sprites`: Runs `python3 tools/compile_bmp_sprites.py`
  - `all`: Runs `setup levels sprites $(BIN_DIR)/$(ROM_NAME)`
- **Clean target**: Cleans all intermediate objects, ROM binaries, and testing artifacts.

## 2. Logic Chain

1. **Resolution Constraints**:
   - The GameBoy screen resolution is fixed at $160 \times 144$ pixels.
   - The game board requires a $20 \times 10$ playfield viewport and a $20 \times 8$ scoreboard (total $20 \times 18$ grid cells).
   - If the grid cells were kept at the original JS resolution of $16 \times 16$ pixels, the required viewport size would be $320 \times 160$ pixels.
   - Therefore, each cell must be represented by a single $8 \times 8$ pixel tile on the GameBoy ($20 \text{ cells} \times 8 \text{ pixels} = 160 \text{ pixels}$ width, $18 \text{ cells} \times 8 \text{ pixels} = 144 \text{ pixels}$ height).
2. **Tile Mapping**:
   - The original sprite sheet contains 32 sprites of $16 \times 16$ pixels ($256 \times 32$ pixels).
   - The GBDK sprite data contains 32 tiles of $8 \times 8$ pixels ($512$ bytes).
   - This results in a direct **1-to-1 mapping** where original sprite $i$ (for $i \in [0, 31]$) corresponds to GBDK tile $i$ in `tiles.c`.
3. **Verification Script Design**:
   - To perform a visual audit comparing these resolutions, we can upscale both the original $16 \times 16$ tile and the GBDK $8 \times 8$ tile to the same size ($128 \times 128$ pixels) using nearest-neighbor scaling.
   - The original tile is upscaled $8\times$ ($16 \times 8 = 128$).
   - The GBDK tile is upscaled $16\times$ ($8 \times 16 = 128$).
   - Slicing the $256 \times 32$ original sprite sheet into 32 distinct $16 \times 16$ tiles yields 16 columns and 2 rows, matching the index mapping of the GBDK tiles.
   - Using cell-specific palettes (BGP for background tiles, OBP0 for sprite tiles) and drawing sprite transparent pixels (index 0) on a solid dark blue background allows for perfect high-contrast outline audits.

## 3. Caveats

- **Sprite sheet height typo in request**: The user request mentioned that `strike_original.png` has dimensions 256x16. However, our programmatic investigation proved that `strike_original.png` (and the base64 string it is decoded from) has dimensions **256x32 pixels** and contains 32 tiles. The design of `verify_graphics.py` has been made robust to handle all 32 tiles on a 256x32 canvas.
- **Pillow Dependency**: The verification script relies on the `pillow` library. However, the virtual environment setup target `test_emu` in the Makefile already handles the installation of `pillow` inside `.venv`, meaning it will be readily available to the implementer.

1. **Verify base64 sprite sheet dimensions**:

   ```bash
   python3 -c "import base64, struct; f=open('dandy-js/strike.js'); c=f.read(); import re; q=re.findall(r'\"([^\"]*)\"', c); b=base64.b64decode(''.join(q[1:])); print(struct.unpack('>II', b[16:24]))"
   ```

   ```bash
   python3 -c "import struct; f=open('dandy-gb/web/strike_original.png', 'rb'); b=f.read(); print(struct.unpack('>II', b[16:24]))"
   ```

   *Expected Output*: `(256, 32)`

   Run the sprite compiler using `make` from the `dandy-gb/` directory:
