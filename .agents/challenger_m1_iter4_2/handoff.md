We designed and added 5 new adversarial tests, bringing the suite to 22 tests.
All 22 tests passed successfully, revealing the following behaviors:
1. **C Comment Backslash Line Continuation**:
   - *Observation*: In `test_parse_tiles_c_backslash_line_continuation_in_comment`, when a single-line comment ended with a backslash (`// comment \`), the parser did NOT treat the next line as a comment. It parsed the commented-out array values `0x11` instead of the active array `0x22`.

2. **C Octal Constant Mismatch**:
   - *Observation*: In `test_parse_tiles_c_octal_values`, the token `012` was parsed as decimal `12` by the Python tool, whereas a standard C compiler interprets it as octal `10`.
   - *Log Output*: `DEBUG: Octal token '012' was parsed as: 12 (expected 10 in C, 12 in naive decimal)`
3. **C Parser Leniency (Missing/Consecutive Commas)**:
   - *Observation*: In `test_parse_tiles_c_swallowed_commas_and_consecutive_commas`, the parser successfully extracted all 512 values even when commas were entirely missing (whitespace-separated: `0x03 0x04`) or consecutive (`0x01,, 0x02`).
   - *Log Output*: `DEBUG: Parser successfully parsed array with missing and consecutive commas (lenient mode).`
4. **JS Concatenation & Spacing Robustness**:
   - *Observation*: In `test_js_extraction_mixed_quotes_and_spacing` and `test_js_extraction_comment_chars_in_string_literal`, the JS extractor successfully extracted base64 data across mixed quotes (`"`, `'`, `` ` ``), highly irregular multiline spacing, and string literals containing literal comment characters (e.g., `"/* not a comment */"`).

### E. GBDK Build Flakiness (Makefile Dependency Race)
- *Observation*: Running `make clean && make` in the `dandy-gb` folder can fail with:
  ```
  make: *** No rule to make target 'obj/tiles.o', needed by 'bin/dandy.gb'.  Stop.
  ```
- *Cause*: `obj/tiles.o` depends on `src/tiles.c`, which is generated by the `sprites` target. However, `obj/tiles.o` has no explicit dependency on the `sprites` target or the generated file `src/tiles.c`. During clean builds, if `src/tiles.c` is not present when Make performs its initial directory scan, the pattern rule for `.o` files is discarded for `tiles.o`, causing the build to fail. Subsequent runs of `make` succeed because `src/tiles.c` is now present on disk (generated by the prior run).

## 2. Logic Chain
1. **C Comment Stripping (Backslash Continuation)**: Standard C comments continue onto the next line if the comment line ends in `\`. Because the Python tool's comment-stripping regex (`//[^\n]*`) only matches up to the newline character, it ignores the backslash line continuation. Therefore, commented-out arrays using this C feature will be incorrectly parsed by the Python tool as active code.
2. **C Octal Constants**: In C, any integer constant starting with `0` is interpreted as octal. Because the Python tool uses a naive `int(t, 10)` fallback for any token not starting with `0x`, it parses `012` as decimal `12`. This creates a semantic mismatch where the verification tool reads different sprite bytes than the Game Boy compiler actually compiles.
3. **JS Regex vs. Division Operator**: The JS comment-stripping regex contains `/(?![*/])(?:[^/\\\n]|\\.)+/` to match regex literals. When it encounters `1 / 2; //`, it matches `/ 2; //` as a regex, consuming the first slash of the comment. This leaves `/ strike.src = ...` in the stream, which is no longer recognized as a comment and gets processed as an active assignment.
4. **Makefile Dependency Race**: GNU Make evaluates the existence of source files during the initial phase. Because there is no explicit file-level dependency or target dependency linking `obj/tiles.o` to the generation of `src/tiles.c`, a clean build has a race condition where the pattern rule fails to resolve `obj/tiles.o`.

---

## 3. Caveats
- **Octal Usage**: While octal constants are technically valid in C, they are virtually never used in auto-generated or hand-written tile coordinate arrays. The impact of this mismatch is extremely low.
- **Backslash in Comments**: Using backslash line continuations in single-line comments is a rare C practice and is discouraged by modern style guides.
- **Division Ambiguity in JS**: Division operators followed by comments containing `strike.src` are highly contrived and unlikely to appear in production sprite files, but this represents a real limitation of regular-expression-based JS parsers.

---

## 4. Conclusion
The graphics extraction and verification tools are **highly robust and correct** for all standard use cases. However, adversarial stress-testing successfully exposed:
1. A **Makefile dependency race** during clean builds due to a missing dependency for `obj/tiles.o` on `src/tiles.c` or the `sprites` target.
2. A **JS parsing bug** where division operators followed by comments containing `strike.src` confuse the regex literal parser.
3. Two **C parsing discrepancies** regarding backslash comment continuations and octal integer literals.

These findings are valuable feedback for improving build system reliability and tool robustness in future iterations, but do not block Milestone 1 completion.
