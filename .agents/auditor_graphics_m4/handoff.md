# Handoff Report: Forensic Integrity Audit of Milestone 4 (Palette & Sprite Integration)

This report details the independent forensic integrity audit of the Milestone 4 implementation.

## 1. Observation

During the forensic audit, the following direct observations were recorded:

1.  **Genuine Hardware Configuration**:
    *   `src/main.c` contains authentic, macro-conditioned hardware palette setup:
        ```c
        #ifdef USE_BLACK_FLOOR
            BGP_REG = 0x1B;
            OBP0_REG = 0xE0;
            OBP1_REG = 0xE0;
        #else
            BGP_REG = 0xE4;
            OBP0_REG = 0xD8;
            OBP1_REG = 0xD8;
        #endif
        ```
    *   Scoreboard font inversion is performed dynamically using bitwise NOT (`~`) in `src/main.c`:
        ```c
        get_bkg_data(i, 1, tile_buf);
        for (uint8_t j = 0; j < 16; ++j) {
            tile_buf[j] = ~tile_buf[j];
        }
        set_bkg_data(160 + i, 1, tile_buf);
        ```

2.  **Robust, Non-Facade Code & Tools**:
    *   `tools/downscale_sprites.py` delegates to `downscale/compiler.py`, which implements a fully planar 2bpp GameBoy tile packer and dynamically writes the `#ifdef USE_BLACK_FLOOR` blocks into `src/tiles.c`.
    *   `tools/verify_graphics.py` contains a complete C-preprocessor emulator and 2bpp GameBoy tile decoder, generating `graphics_audit.png` and `graphics_audit_dark.png` dynamically from `src/tiles.c` using nearest-neighbor scaling.

3.  **Thorough and Honest Testing**:
    *   Unit and integration test suites run successfully:
        ```
        Ran 176 tests in 6.814s
        OK (expected failures=3)
        ```
    *   The test suite includes `@unittest.expectedFailure` blocks for advanced parser edge cases (e.g. swallowed commas, division operator ambiguity), demonstrating complete transparency.
    *   `tests/verify_emulator.py` boots a real GameBoy ROM in PyBoy, resolves WRAM addresses dynamically from `.map` files, and asserts state after simulated joypad input.
    *   Running `make clean && make test_emu` successfully compiles both ROM targets and passes all E2E emulator tests:
        ```
        Running PyBoy automated emulator E2E tests: Classic DMG...
        Ran 2 tests in 0.163s
        OK
        Running PyBoy automated emulator E2E tests: Atmospheric Dark...
        Ran 2 tests in 0.190s
        OK
        ```

4.  **Concurrency Race Condition**:
    *   A clean build can fail with:
        `src/dandy_core.c:101: error 257: Failed to open output file 'obj_dark/dandy_core.asm' (No such file or directory)`
        because the object compilation pattern rule `$(OBJ_DIR)/%.o: $(SRC_DIR)/%.c` does not declare a dependency on the directory creation target (`setup`), leading to race conditions under parallel make execution.

## 2. Logic Chain

1.  **No Cheating / No Facades**:
    *   Since the codebase directly sets actual GameBoy hardware registers (`BGP_REG`, `OBP0_REG`, `OBP1_REG`), programmatically generates inverted fonts in VRAM, and contains a genuine, mathematically correct planar 2bpp downscaler/packer, we conclude that there are NO facade or dummy implementations.
    *   Since all test suites execute dynamically, verify actual RAM values in a headless PyBoy emulator, and delete/regenerate output audit sheets from scratch, we conclude that there is NO hardcoding of expected test results or pre-populated verification outputs.
2.  **High-Fidelity Visual Audits**:
    *   Since the audit sheets are generated by parsing, preprocessing, and planar-decoding `src/tiles.c` and upscaling by 8x using `NEAREST` neighbor, the visual comparison sheets are genuine.
3.  **Build system issue**:
    *   Since GBDK compilation succeeded on a sequential clean build but failed on parallel runs due to directory omission, there is a race condition in the Makefile, though it does not constitute an integrity violation.

## 3. Caveats

*   **Emulator dependency**: E2E testing relies on PyBoy and Pillow, which must be installed. The `Makefile` installs these automatically inside a local `.venv` using `uv`.

## 4. Conclusion

The Milestone 4 implementation is **CLEAN** of any integrity violations. The graphics conversion, palette configuration, sprite transparency, and E2E verification are authentic and function correctly. A minor concurrency issue was identified in the `Makefile`, which should be resolved to improve parallel build stability.

**Verdict: CLEAN**
